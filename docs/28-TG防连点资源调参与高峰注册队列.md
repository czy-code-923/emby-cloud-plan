# 28 TG防连点、资源调参与高峰注册队列（v7.1）

日期：2026-11-19。本篇补齐TG交互的专门防护，以及发放100个或更多邀请码后的注册高峰设计。仍是待开发方案，离线模型和原型不是生产限流器；媒体第21篇、交易第16篇、独立总控第25篇与更新助手第26篇继续适用。

## 1. 三种问题分别限制

| 问题 | 主要措施 | 不能混为一谈 |
|---|---|---|
| 同一人连点、脚本换按钮/回调ID | 真实TG身份总预算、动作预算、短合并、单人写入互斥、业务幂等 | 不是前端禁用按钮几秒就安全 |
| 猜邀请码/兑换码/安全码，重放旧确认 | 高熵引用、归属/版本/epoch校验、失败预算/冷却、一次性确认、持久核销约束 | 不能因缓存命中跳过权限；Bot流量不能拿共享Telegram IP分用户 |
| 100人同时合法注册 | 短接收、有界持久队列、轮巡公平调度、少量worker、资源熔断与状态查询 | 不是给每个人起线程/协程、占一个DB连接或同时调用Emby |

内存升级后**可能需要调缓存、队列容量、预取和并发预算**；单人安全频率、验证码失败数、成员/每日名额/同播数和Telegram发送限制不会按内存自动放宽。

## 2. 入口与处理链

```text
单一轮询收件者 / 校验secret header的Webhook
→ 请求体/解析并发/全局接收上限 → 验证真实TG身份
→ 用户原始频率 → 对象权限与回调上下文 → 动作限额/合并
→ 有界持久收件箱/唯一业务操作 → 快速按钮回应
→ 专用任务队列 → 有限worker → 事务结果/outbox通知
```

Webhook可将`max_connections`设为4起步，但它仅限制Telegram投递连接；应用仍需独立的解析、执行、队列和DB连接预算。轮询首期继续保留，批量读取也只能按收件箱空位接收，持久完成后再推进offset，不一次取100条后为100人创建长期任务。

secret、体积和廉价身份检查在高成本反序列化、口令哈希和外部API之前。无效/不支持输入有界处理并明确安全拒绝，不能永久503重复风暴；有效操作未持久接收且容量已满才返回临时失败，让Telegram重试。2xx表示已持久接收或明确安全拒绝，不代表账号已开通。

可处理的更新类型显式列出；群内普通聊天不默认进入业务队列，不把陌生消息自动变成完整成员。Mini App API通过initData认证后的同一TG身份共享操作预算，不许换HTTP入口绕过Bot限流。多副本必须共享原子预算与全局队列上限，不能每实例各放一份额度。

## 3. TG动作默认限额

以下为S档2C2G的**提案初值**，均在总控显示单位/范围/作用域；不是Telegram官方规定。原始接收、基础鉴权、幂等、有界资源和安全失败冷却属于硬边界；额外行为惩罚先观察72小时再决定执行。

| 层/动作 | 初值 | 超限行为 |
|---|---:|---|
| 所有动作，按bot＋真实TG user | 同时满足20次/10秒、60次/分钟 | 轻量拒绝，聚合计数，不创建新的业务任务 |
| 普通菜单/账户/地址导航 | 10次/10秒、30次/分钟 | 复用允许缓存/提示稍后，不能反复查Emby/网盘 |
| 同人同动作同对象 | 2秒合并窗口，最多1个在途写操作 | 返回原操作/处理中；不能多加积分、开户或发码 |
| 写操作（签到、模式、码等） | 3次/10秒、10次/分钟 | 明确限频；已提交操作按原operation_id查结果 |
| 邀请/兑码核验失败 | 5次/10分钟，之后此身份15分钟冷却 | 统一失败文案，不泄露码存在/归属；仅限相关验证功能 |
| 安全码错误 | 沿用5次失败、锁15分钟，单独统计 | 限制敏感操作；不误停普通帮助/既有播放 |
| 注册排队状态 | 至少15秒一次，建议20秒±20%抖动 | 返回缓存状态/下次查询时间，不重建队列任务 |
| 反馈消息 | 同人同限流原因至少30秒合并 | 正常负载下仍及时回应callback结束等待，不每击发一条聊天消息 |

作用域不能仅用callback_query.id、message_id、随机request_id或用户名；脚本不断换这些值仍消耗相同用户预算。已鉴权的短合并复用消耗原始动作额度，不再记一次新写操作，但仍有回应/资源预算。IP只在自有HTTP入口做粗防护，不能把Telegram共用来源IP等同用户，也不因群内一人连点封整个群。

callback_data只放短不透明引用，至少128bit随机，服务器绑定actor、动作、对象、版本、credential/policy epoch、允许消息/聊天上下文、300秒有效期；引用不能直接携带秘密或信任客户端金额/UID。每次缓存复用仍查最新权限/撤销；过期/他人/被篡改按钮不运行写操作。二次确认一旦核销不能重用，执行结果已存在时返回脱敏原结果。

短合并不是永久幂等：签到使用成员＋自然日，积分兑换使用已确认业务订单，码使用持久claim唯一键，注册使用身份＋服务唯一活跃intent。用户以后明确发起另一笔合法续期仍允许；网络重试不能被误当新订单。近期update_id去重以48小时为保留目标，并有独立磁盘预算/初始10万已处理记录上限；超过上限可提前清最旧已完成transport记录，不能丢未处理消息。短期去重不保证覆盖全部历史，长期业务唯一键/已消费确认/claim事实仍必须保留，避免早清记录导致重复写。

口令哈希先过廉价限额、再进入独立小并发执行池，不能占Bot主事件循环；不因内存升级私自降低/更改哈希参数。可疑行为只短时冷却相关动作，管理员不免基础限流；临时例外须写原因、范围和到期，不自动永久封号、删账号或封网段。

## 4. 回应、发送和失败降级

正常负载下收到按钮后目标2秒内调用answerCallbackQuery（工程目标，不是官方固定时限），长任务显示“已排队/处理中”。缓存拒绝/繁忙也做有预算的callback回应；若平台/网络已拥塞则尽力回应，过期按钮提供新入口，不承诺无限流量时所有按钮秒回。

普通聊天消息初值20条/秒全Bot、单聊天至少间隔1秒、群15条/分钟，并为callback回应/安全提示保留独立通道；不能把这些值当所有Bot API方法统一的官方上限。429按实际method/chat/global范围与retry_after退避，普通广播不能饿死控制回应。重复点菜单优先修改原消息/返回缓存，攻击计数按分钟聚合，不每次写DB/通知管理员。

状态缓存和风控键有字节与数量双上限；字节先到即停增长，未知ID不能无限建键。缓存满/重启/驱逐不能让冷却用户拿到新敏感写额度：关键nonce/核销事实持久，短期限流需有保护性保留或保守拒绝新敏感写，不能任意LRU删除后视为零次。DB/限流状态故障时不直接绕过开户/扣分/核销，已有播放按原有有界降级策略处理。

## 5. 内存档位与资源预算

有效内存取宿主/服务容器等适用限制中的最小值，标明采样范围和时间；不能用VPS宣传值或空闲时内存判断。下表是起始模板，实际还受CPU、Emby延迟、DB池、哈希预算、磁盘及全栈峰值约束。

| 档位 | TG风控状态上限 | TG无秘密回复缓存 | 持久收件箱未结数 | 持久注册队列未结数 | 仅驻内存预取引用 | 建议开户worker / 哈希并发 |
|---|---:|---:|---:|---:|---:|---:|
| 1GB XS | 8MiB / 5000键 | 4MiB | 64 | 128 | 1 | 1 / 1；不推荐完整栈 |
| 2GB S | 16MiB / 10000键 | 8MiB | 128 | 256 | 2 | 1 / 1 |
| 4GB M | 32MiB / 20000键 | 16MiB | 256 | 512 | 4 | 1～2 / 1 |
| 8GB L | 64MiB / 40000键 | 32MiB | 512 | 1024 | 4 | 2 / 1～2 |
| 16GB+ XL | 128MiB / 80000键 | 64MiB | 1024 | 2048 | 8 | 2～4 / 1～2 |

键数不保证在给定MiB里全部装下，要测对象开销。TG风控缓存、TG回复缓存和媒体网关原有16MiB缓存分别核算，不能重复使用同一块余量。表内队列记录是DB里的小任务，不是同数量驻内存执行栈；每条规范化payload最多2KiB，不存密码/安全码/邀请码原文，实际驻内存还有parser/worker/DB/哈希/媒体峰值，必须合计。

### 5.1 三种模式和自动调整范围

| 模式 | 设置页行为 | 自动改变什么 |
|---|---|---|
| MANUAL 手动 | 管理员设预算，显示实际限制/待应用 | 不自动提高保存值；已启用资源保护仍可暂停新开户/回收无秘密缓存 |
| RECOMMEND_MANUAL_APPLY 推荐后手动应用（默认） | 自动识别档位/瓶颈，显示建议/证据/差异，管理员确认发布 | 不自动提高缓存/队列/worker配置值，内存升级也不会直接应用 |
| AUTO_BOUNDED 边界内自动（可选） | Owner先设各项最小/最大/作用域/是否允许增长，显示每次原因和回退 | 默认只调风控/回复缓存字节与预取；队列和worker增长另需明确勾选和证据 |

自动增长先确认容器/服务确有可用余量，稳定10分钟后每次最多向上25%，两次增长至少间隔10分钟；只能到Owner批准上限，未知指标/持续swap/OOM不增长。队列增容还须DB磁盘/最老等待时长支持，不能以更长队列掩盖服务故障；worker增并发需CPU/Emby延迟/DB可用连接/哈希峰值共同允许。不能偷偷扩大容器RAM、DB连接池、全局重任务预算或第三方API速率。

低可用内存<256MiB或有效cgroup使用≥85%起始触发停止领取新开户，保留已排队意向；恢复要求可用≥384MiB且使用≤75%稳定120秒，并确认来源健康。实际阈值允许按实例基线调节，1GB完整栈可能长期无法满足，应提示外置组件/升级，不为恢复任务偷偷降低安全余量。缩缓存只删可重建内容，不能清nonce/冷却/账本；降低队列上限不丢已收任务，只停新接收。

无论内存多大，单人点击/失败阈值、成员/每日名额、商品/已售容量、同播/来源签发、Telegram发送限制都不自动放宽。总控必须把“预算自动调节”和“业务限额/安全频率”分开。

## 6. 100+邀请码发放前预检

发行批次页列出：本次码数、每码次数/归属/截止、资格型或预留席位型、现有成员、在途开户席位、已售未兑预留、剩余名额、每日剩余额度、可排队上限、最老等待和预计分批计划。超过已验证承诺容量的预留席位型发放拒绝；资格型允许明确不保证即时开户，并让管理员确认说明。

**默认仍是20成员、每日成功3、同播2。发100码不会自动改成100成员或100路播放。**若要最终开放100个实际成员，先依据已验证使用规模/同播证据手动增加相关名额；开通速度也单独设置，不能把“100个码”解释成已经承诺100个即时可用账号。剩余只有20席时多余资格进入有界候补，付费注册码此前预留的资格继续履行。

邀请码生成/导出也限制批量和任务内存，流式生成高熵值/分离加密下载，按批次幂等，不把10000个明文一次塞入TG或前端表格。批次导出需要权限/短时下载/审计，泄露时可撤未用码并保留已核销历史。

## 7. 注册接收、排队与公平轮巡

### 7.1 接收不开户

验证私聊/网站已绑定身份及资格后，用短DB事务查该身份原有intent、验证开关/邀请、检查**未结总数含排队、等待配额、leased、退避、结果不明**，然后创建唯一排队单。队满前必须拦住，不能只数QUEUED漏掉正在执行的人；一人一单，重复点击/重试/换request_id只返回原单，不重复预留。

API返回202＋ticket_id＋状态＋建议20秒查询时间（服务端最短15秒）；Bot修改原消息并提供“查看进度/取消”。位置仅为近似，不能暴露他人资料或保证准确完成时间。浏览器不常驻每人WebSocket，关闭TG不丢队列，重启后从数据库恢复；状态读缓存、带抖动，不能100人每秒各扫一次全表。队满返回可读繁忙/重试时间，网站用429＋Retry-After；不能另建无上限“等待队列的队列”。

免费邀请待使用次数与intent关联，成功才消耗，安全取消/过期/拒绝后释放。资格不能因反复查进度无限延长；初始最长等待24小时，已明确维护/资源事故暂停计时或统一延期并通知。待执行重新验证到期/撤销/政策；失效不悄悄通过。业务席位只在准备开通时短预留，不让长队列提前占满所有免费名额。已售注册码沿用售前承诺席位，核销时转换该预留，不能再重复扣一席。

### 7.2 调度只领取可执行任务

默认按就绪批次round-robin、同批FIFO；如有已预留的付费资格，可按最多连续2个付费、再给一个同样可执行的免费任务的规则调度，保证轮巡，不让一个大批次饿死其他人。无容量/日额度/资格待审的任务显示WAITING_CAPACITY/WAITING_POLICY及下次检查时间，不占worker睡到明天，不高频失败重试。

单机初始1个开户worker、每次领取1个、最多预取2个引用、空闲2秒±抖动检查；通知仅作唤醒提示，丢通知仍能轮询恢复。索引覆盖状态/run_after/批次/顺序；`FOR UPDATE SKIP LOCKED`只用于短领取事务，配全局并发计数/租约/fencing。公平性由调度器实现，不把SKIP LOCKED或数据库查询顺序当公平保证。

DB池沿用S档4个连接并预留交互/账本能力；领取后释放连接再调用Emby，不为每个等待用户保持连接。多个worker/副本共用实际并发上限；租约过期先隔离旧执行者和核实外部效果，不能仅超时就让第二个worker重复创建。

### 7.3 开户状态与一致性

```text
QUEUED → VERIFY_ELIGIBILITY → RESERVE_READY_SEAT
→ CREATE_EMBY_ACCOUNT → APPLY_POLICY → VERIFY_MAPPING
→ COMMIT_SUCCESS → NOTIFY_ACTIVATION
分支：WAITING_CAPACITY / WAITING_POLICY / RETRY_WAIT
      RECONCILING / CANCELLED / EXPIRED / REJECTED
```

准备开通时原子检查成员容量、已售预留、每日成功数与每日在途额度、邀请码/批次有效性、每人唯一账号，预留本次执行额度；成功才把在途额度转成功计数和消耗邀请，失败已知无外部效果才释放。入队本身不算每日成功注册，不能绕过配额，也不占一个长期Emby账号。

外部创建使用稳定操作ID/明确归属，超时结果不明先进入RECONCILING，查询映射及本次执行证据；Emby未提供已验证的幂等创建契约时不假称“重试一定安全”。查不清就人工处理，保留席位/邀请占用，不盲目再建。创建后本地提交失败，恢复需认领**有证据属于本操作**的账号或补策略；不能凭同名认领/删除外部用户。故障隔离自己的待激活账号，历史账号/观看史不删除。

密码不从TG收集，不进队列。若上游开户需要初始秘密，仅在执行时产生，受保护短用并按需清理，最终通过一次性HTTPS页面设置密码、安全码/恢复码；进度通知不发默认密码。设置完成并查证Emby策略后成功，重复通知只发送激活入口/原结果，不再建号。

### 7.4 重试、取消和保护

已知可安全重试的临时错误采用5/15/45/120/300秒＋抖动，最多5次；上游429以其retry_after为下限。配额/关闭/授权错误等待政策或人工，结果不明不得按普通重试处理。用户仅可取消本人尚未执行意向并释放自己的预留；正在创建/结果不明返回处理中，取消不盲删已有账号。

Emby/DB/磁盘/内存异常触发暂停新领取和必要时停新接收，保留已接收排队单，已完成账号与播放不随机踢掉。资源/数据库恢复并稳定后续跑；断网、进程重启、更新维护均有检查点，恢复不丢邀请码消耗与已售承诺。人工暂停、恢复、重排、撤批次均有权限、影响预览、原因和审计。

## 8. 一次100人的示例与承诺边界

- **沿用默认策略**：100个有效资格入有界队列后，首日最多成功3人且最终受20席和已售预留约束；其余显示等待每日额度/容量，不自动改规则。真正大批放号前应调整经验证的活动计划或分批通知，不能发码后隐藏预计等待。
- **管理员已批准100名额及日额度**：同一瞬间提交也仍是有界落库、单worker逐个创建，2个引用预取；用户关闭界面不影响处理。若单人全部流程假设2秒，顺序模型是约200秒，**不是实际耗时保证**；哈希、Emby延迟/限流、通知、失败/重试都会延长。
- **超过队列上限**：S档未结上限256，含执行/退避/结果不明；第257个新意向获得稍后重试，已在队列的用户重复提交仍返回原单。需要2000人活动时可分批开放/按时间窗预约或先扩容测量，不自动在RAM堆2000个任务。

## 10. 必须完成的验证

## 11. 一手依据与本项目选择

2026-11-19复核：[Telegram Bot API](https://core.telegram.org/bots/api#callbackquery)要求回应callback结束客户端等待，Webhook支持secret_token及max_connections，返回的retry_after用于限频等待；这些提供机制，不给本项目的20次/10秒或2秒回应目标背书。[Telegram FAQ](https://core.telegram.org/bots/faq#my-bot-is-hitting-limits-how-do-i-avoid-this)给出普通聊天/群/广播的发送限制说明，实际429仍需按方法处理。[PostgreSQL SELECT](https://www.postgresql.org/docs/current/sql-select.html#SQL-FOR-UPDATE-SHARE)说明SKIP LOCKED可用于队列表，但公平性/全局配额/外部效果一致性仍由业务实现。[Docker资源约束](https://docs.docker.com/engine/containers/resource_constraints/)支持核验实际内存限制。

本篇所有阈值、档位、队列公平策略和保护流程属于项目设计，并非已部署功能或Telegram/Emby的原生保证。
