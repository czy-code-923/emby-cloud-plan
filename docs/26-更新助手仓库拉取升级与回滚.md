# 26 更新助手：仓库拉取、升级与回滚（v7最终设计）

日期：2026-11-19。**现有`emby-cloud-plan`是方案仓库；未来程序仓库尚未创建。**本轮不创建程序仓库、不部署更新器。以下定义未来实现，仓库地址/ID/签名身份均待配置，实际更新状态为`UNCONFIGURED`。

## 1. 目标、入口与默认模式

网页总控有独立“更新助手”，展示当前/候选应用版本、前后端/API/配置schema/业务DB schema、Emby/媒体适配器/数据库版本、来源提交、镜像摘要、兼容矩阵、变更说明、备份/预检、维护窗口、执行日志和回退资格。Bot仅可通知摘要，不能凭群消息触发宿主更新。

| 模式 | 自动做什么 | 应用条件 |
|---|---|---|
| OFF | 不检查、不下载、不应用 | Owner可随时启用检查，不中断已进入不可取消提交点的步骤 |
| CHECK_ONLY（初始策略） | 配好可信程序仓库后每6小时±抖动检查稳定Release，通知候选 | 当前仓库未配置，连检查请求都不发；发现候选不改生产 |
| AUTO_DOWNLOAD_MANUAL_APPLY（推荐首期） | 自动获取并验证发布清单、源码快照/预构建镜像，完成预检 | Owner查看差异/MFA后预约或立即受控应用 |
| AUTO_APPLY_IN_WINDOW（可选） | 维护窗口内自动应用已满足策略的允许版本 | Owner预先批准组件/通道/风险范围，所有Gate实时复核；重大/破坏迁移仍人工确认 |

自动应用可以实现，不要求每次再点确认；但必须有事先限定的策略，不能把任意新提交、版本号写着patch或“安全更新”标签当自动许可。缺有效备份、兼容性或资源不满足时暂停并提示原因，绝不悄悄绕过。

## 2. 仓库和组件边界

| 对象 | 来源和管理方式 | 是否随业务应用自动升级 |
|---|---|---|
| 方案文档 | 当前GitHub方案仓库，保留设计历史 | 否；文档同步不执行代码、不升级VPS |
| 业务程序/前端/worker | 未来独立程序仓库＋CI构建/Release/OCI镜像；同一发布清单固定组合 | 可按批准策略整体发布，前后端兼容不能各追latest |
| 可信发布/版本清单 | 独立校验身份/签名的清单，绑定仓库稳定ID、提交、版本、构建、摘要、schema和升级限制 | 必须先验证再选择候选，不信未签名版本文件 |
| Emby/OpenStrm/OpenList等 | 各自上游固定版本与适配矩阵，必要时手工验证/独立维护窗口 | 默认否；不会因为业务更新偷偷升Emby或改网盘驱动 |
| PostgreSQL/Docker/系统包/防火墙 | 单独基础设施变更，DB主版本有迁移/演练 | 默认否；不在普通“更新”按钮隐式执行 |
| 更新执行器自身 | 独立版本/信任根，双槽或独立受控维护 | 默认人工；应用更新不能修改信任根后自批任意代码 |

程序仓库配置留空，不拿当前方案仓库地址作占位默认。配置来源时Owner校验HTTPS主机/仓库控制权、稳定repository/owner ID、允许Release通道和签名/构建工作流身份；记录审核与版本。私库用最小只读Token/GitHub App，下载凭据不写URL/日志，不给推送权限。

## 3. “自动拉取仓库”的具体实现

推荐生产消费**CI预构建、固定摘要、已验证来源的发布产物**，2C2G不在维护时编译大型前后端。GitHub Release是候选发现源，不是可信性证明；只选允许通道、非draft/非prerelease且清单匹配的版本，预发布需Owner单独启用。

若需要同步源码，执行器在专用只读来源目录`fetch`仓库，解析允许tag到精确commit，再获取此commit快照；它与运行目录、数据目录、secrets分开。禁止对线上工作目录直接`git pull`后执行仓库任意脚本，禁止覆盖`.env`、业务数据卷或自定义配置。submodule/LFS/远程include默认关，确需引入则显式锁定来源和摘要；下载与解包处理路径穿越、符号链接逃逸、压缩炸弹、文件数/体积限制。

源码构建是手动高级路线：在隔离CI/构建机完成受控构建、锁依赖、扫描和签名后再发Release；不能因为预构建产物缺失，更新器就在宿主root下自动安装依赖/运行hooks。现有业务容器源码卷不热替换，发布使用不可变产物。

## 4. 发布清单和信任验证

每个Release包含机器可读清单：release_id、单调release_sequence、版本/通道、issued_at/expires_at、来源repository_id/owner_id/commit/tag、构建工作流身份/提交、各架构产物大小/SHA-256或OCI摘要、前后端/API配套版本、最低执行器/当前版本、DB/config schema读写范围、迁移ID与校验和、是否可逆/是否破坏、资源/空间估算、探针、允许回退目标及最低安全版本。

验证顺序：可信身份/签名或构建证明→清单时效/撤销和回放保护→目标主机架构与版本→下载到staging→字节摘要/大小→产物身份→本地受限模板与权限差异→预检。可选择经实际支持验证的GitHub Artifact Attestations（限定repo/owner稳定ID、signer workflow、source commit/ref/predicate）或离线签名清单＋预置公钥；不是“仓库里同时提供文件和SHA256就可信”。发布密钥轮换由旧信任根授权并保留过渡，撤销和紧急恢复有独立本地入口。

签名证明来源与完整性，不保证发布者没引入漏洞；仍需代码审核、CI验证、最低安全版本和兼容策略。正常自动更新不允许旧sequence/低于安全下限；有理由的回退使用明确批准、仍可信的目标，不能关掉所有验签。时钟偏差过大或无法更新可信时间/撤销信息超过允许新鲜度时停止新自动应用，已有业务继续运行。

## 5. 网页交互和策略字段

“概览、更新来源、自动化策略、候选详情、预检/备份、执行记录、回退/救援”七个页签。按钮是检查、下载验证、预检、预约、取消未应用任务、应用、查看结果、兼容回退；候选不存在/未配置/校验失败时相应按钮禁用并显示原因。

可配字段：程序仓库/稳定ID、Release通道、信任根/构建身份引用、检查间隔/抖动、下载镜像/受信镜像站（仍验原产物签名）、代理引用、下载限速/空间上限、自动应用允许组件/风险、维护时区/窗口、黑名单/版本固定、活跃播放处理、预检阈值、备份新鲜度、重试/超时/观察、通知目标和回滚保留。不能输入任意宿主命令、任意Compose/YAML片段或下载后执行脚本。

当前模式为“检查策略已设计，程序来源未配置、执行器未实现”；空值不猜仓库。保存未来仓库配置只产生草稿，不开始执行，验证成功并发布配置后才进入检查计划。下载和安装权限分开，Ops可看/下载，应用由Owner或`RELEASE_APPLY`范围承担，信任根/基础设施变更仍Owner。

## 6. 持久状态机与互斥

```text
UNCONFIGURED / DISABLED
→ IDLE → CHECKING → CANDIDATE → FETCHING → VERIFIED
→ PREFLIGHT → AWAITING_APPROVAL / SCHEDULED → PREPARING → QUIESCING
→ BACKUP_VERIFIED → APPLYING → HEALTH_CHECK → OBSERVING → SUCCEEDED
失败分支：REJECTED / BLOCKED / FAILED_SAFE / ROLLED_BACK / NEEDS_RECOVERY
```

记录operation_id、来源与目标版本、manifest_hash、策略版本、审批/预约、每步检查点、锁owner/fencing token/租约、原/新产物、备份ID/水位、日志摘要和最终applied版本。重复点击/超时只查询同一操作；单环境只能一个应用者。备份/恢复/迁移/域名切换/重大重扫与更新使用同一变更协调器；重任务用单并发预算。

执行器与Web进程生命周期分开：Web重启不杀死更新；Web恢复后按操作ID重连。租约超时不等于可直接启动第二个更新器，必须先核实旧执行者退出/隔离并fence；重启后从已持久检查点探测实际状态，不猜上一步未执行。取消只在安全边界生效，已提交数据库迁移不会被浏览器“取消”撤回。

## 7. 应用前必须通过的Gate

| 检查 | 必须满足 | 不满足时 |
|---|---|---|
| 来源与签名 | 来源/产物/提交/清单身份匹配、无撤销、有效时效 | REJECTED，不运行任何候选代码 |
| 版本组合 | CPU架构、API/前端/worker/config/DB兼容，跳版本路径明确 | BLOCKED，按已验证中间版本升级 |
| 资源/磁盘 | 实际可用RAM/磁盘支持下载、解压、快照、回退；估算包括旧/新镜像峰值 | 等待/人工扩空间，不全局prune、不删数据卷 |
| 未决变更 | 无迁移/恢复/网络切换、待核与账本异常已安排，更新锁可得 | 排队/阻止，不两套执行者争抢 |
| 有效备份 | 排空后的本次升级点快照完成、manifest/解密/控制总额有效；schema变化需隔离恢复证据及初始策略要求的异地回执 | 阻止写迁移；前次定时备份或“有备份文件”不足够 |
| 业务排空 | 注册/下单/核销/自动扣分/清退/媒体写入受控暂停，在途事务完成 | 到超时推迟；不丢弃已付款/已收消息 |
| 回退能力 | 明确旧程序可读新schema，或维护隔离直到迁移验收；救援材料在Web之外 | 禁自动应用，转人工维护方案 |
| 权限变化 | 本地受控部署模板无新增未知挂载/端口/capability/privileged/远程include | 阻止自动，需独立代码/模板审查 |

## 8. 2C2G推荐更新流程

1. 非高峰后台检查并流式限速下载，不打断播放；重扫/大备份与下载/解压错峰。VPS只拉预构建产物，下载失败可校验后续传，重试有上限与退避。
2. 显示版本差异、组件/数据库影响、预估临时空间与维护条件。保留上一正常镜像/部署清单，清理仅限经路径/归属校验的本项目过期staging，不能执行全局Docker prune。
3. 维护窗口满足Gate后暂停新销售/注册/claim/扣分/清退/重任务，排空业务写请求。TG入口可先持久化已验收更新后延迟处理；若暂无法持久化Webhook请求则返回可重试失败，轮询不提前推进offset，不能先成功确认后丢更新。重复由inbound/outbox幂等处理。
4. 生成跨业务边界一致的本次升级快照/水位；不能只沿用数小时前的定时备份。PostgreSQL一致dump不代表Emby/适配器SQLite和外部核款一起原子，必要时短停各自写入并写入共同检查点。备份产物与解密能力通过后才能动schema；初始策略还要求schema变化前取得异地回执和对应版本的隔离恢复证据，尚无异地目标时阻止此类自动更新，不影响只检查/下载。
5. 按清单执行已批准迁移与固定模板换程序，2GB默认原地短维护更新，不承诺蓝绿双栈或零停机。依赖DB/网盘/Emby不重启除非另有批准变更，媒体容器原样运行也仍需测试其API影响。
6. 先只开内部/测试路径，验证schema、配置、权限和探针；成功后恢复用户入口、单一worker/Bot收件者、通知/计划任务，观察15分钟起始值，再标记SUCCEEDED。API上线但账本/核销检查失败不能标绿。
7. 在途302播放是否能继续取决上游直链TTL、播放器和线路；更新前可选择等待活跃播放结束或到截止后推迟。重建网关/Emby可能断流必须提示，不承诺全部客户端无感。

## 9. 数据库迁移与回退

优先expand→兼容双版本→延后contract：新增字段/索引和可回填结构先上线，清旧字段/不可逆转换单独人工维护。迁移有唯一ID/校验和/租约/状态、短锁/超时、可恢复检查点；长回填限制批次，不把半执行误标完成。数据库主版本升级不属于普通应用自动更新。

**程序回退**：若旧程序已验证可读写当前schema，切回上个固定摘要和兼容配置版本，保留全部新业务数据。**配置回滚**：生成一个新的配置版本，不倒回业务数据库。**数据恢复**：独立灾难恢复流程，先停写，导出/核对恢复点后新增订单、核款、claims、积分、撤销和任务水位；不能自动还原旧库吞掉新交易。

若新版本健康失败且schema不兼容回退，进入NEEDS_RECOVERY，冻结受影响写入、保护数据与日志，使用独立执行器/本地救援；不要为了“自动回滚成功”强行运行旧程序。不可逆迁移只有在全程停写且恢复损失/对账计划经明确确认时才能执行恢复；恢复旧快照还必须核对外部真实到账和最新撤销日志，防止二次发码/码复活。

## 10. 健康验收与恢复顺序

静态检查前后端版本与静态资源摘要；内部readiness检查DB连接/schema、任务锁/队列、设置应用版本、凭据可解；业务探针检查普通用户/管理员权限隔离、Emby连接/授权样片、积分/权益只读对账、核销唯一约束和未决订单水位。生产探针不自动产生实收、兑换真实付费码或扣真人积分；写流程在隔离测试租户/测试数据完成。

恢复顺序为身份/只读→业务写准入→唯一worker/收件者→通知/定时任务→媒体重任务。对账错误则保留受影响写冻结，其他未受影响播放按已验证降级策略继续；重启容器running不等于业务健康。故障通知至少站内执行记录＋独立受限通知目标，通知失败不触发重复安装。

## 11. 执行权限、供应链和救援

Web只发固定operation_id、manifest_hash、目标和短期票据给受限更新服务，不能接Docker socket、root终端、任意Compose文件/路径。宿主更新服务若需Docker权限，它实际上具有强宿主能力，应独立Unix socket、白名单命令/固定模板、来源身份验证、最小文件访问和系统审计；不把“只读挂载Docker socket”当无害隔离。

不直接加载仓库的远程Compose include/extends、不运行curl-pipe-shell，不由候选应用覆写宿主执行器/信任根。模板只允许已审核服务、挂载、网络和资源字段；预解析不读取任意宿主文件、不将展开的环境secret写日志。更新源/镜像代理限定HTTPS和已验证目的地，防SSRF/DNS重绑定与重定向凭据泄漏。

本地受限CLI/服务单元提供`status/resume/abort-before-commit/rollback-compatible/diagnostic`等固定操作；无Web时也能读状态和恢复旧可兼容产物。部署应预留救援VPN/隧道、离线Owner恢复资料、密钥和上个已知正常清单；程序损坏不能导致唯一备份密钥丢失。

## 12. 维护模式、定时和多节点

维护窗口以`Asia/Shanghai`为默认、半开区间定义，跨日/时钟跳变用可靠UTC计划实例ID和单调超时处理。当前仅单环境单节点；未来多节点先升级独立测试/金丝雀，再滚动兼容节点，控制面/worker/数据库分别排序，共享schema兼容范围未验证不滚动。备份节点只接加密快照，不因升级失败自动升为可写主库。

禁自动更新或撤仓库Token立即阻止下一阶段拉取/应用；正在原子替换/DB提交中则到安全边界暂停并标明实际状态。GitHub不可达、限流、签名服务故障均保持当前已知正常版本，支持经相同验签流程的离线导入包，不改为不验签下载。

## 13. 发布侧需准备的内容

未来程序仓库建立后，应具备：受保护发布分支/标签、锁依赖、多架构CI、必要功能/迁移测试、镜像/前端构建、SBOM/漏洞处理、来源证明或签名、版本/兼容清单、Release说明、撤销与最低安全版本、隔离升级/回退演练、恢复指南。仅提交代码到main不生成可自动安装版本，未生成可信产物时助手只提示，不自行猜下载地址。

## 14. 必须实施验证的异常用例

| 场景 | 预期行为 |
|---|---|
| 方案仓库被误填为程序仓库、程序仓库为空 | 类型/来源校验拒绝或UNCONFIGURED，不执行文档内命令 |
| tag移动、包被替换、错仓库/工作流、旧清单重放、密钥撤销 | 摘要/身份/时效/sequence验证拒绝，不进入候选运行 |
| 私库Token失效、GitHub限流/网络中断、下载断电 | 当前版本不变；脱敏、退避、校验后重试，无无限循环 |
| 两管理员重复点更新、执行器掉线/重启、租约超时 | 单操作/单fenced执行者；探测检查点，不能并发跑迁移 |
| 磁盘不足/OOM、压缩炸弹、目录逃逸、远程Compose提权 | 预检/配额/解包/模板拒绝，不删数据卷、不改变宿主权限 |
| 备份无法解密、异地复制失败或恢复水位不够 | 按本次备份策略阻止应用；不能把上传进度100%当通过 |
| 更新中仍有核款/claim/签到/源任务、Webhook重试 | 排空或持久幂等延迟，恢复不双发/漏发、不误清退 |
| 迁移中断/锁超时、新版本不健康、Web自身起不来 | 固定检查点恢复/兼容回退；不兼容进入救援，旧数据受保护 |
| 新版本已接收订单后要求回旧库 | 拒绝自动旧库覆盖，先停写并对账新交易/claim/撤销 |
| 更新后账号/库/积分看似正常但Emby策略不同步 | 不标验收通过；显示desired/applied差异并处理 |

## 15. 一手参考与使用边界

以下于2026-11-19核对，作为设计依据，不表示本项目已接入对应产品：

- GitHub Release可用API查询，私有仓库读取需要相应只读权限；Release列表与普通tag不同。[GitHub Releases API](https://docs.github.com/en/rest/releases/releases)
- 构建证明必须实际验证来源身份；可限定仓库、工作流和源码提交等条件，验证器版本/参数在实施时固定。[GitHub CLI attestation verify](https://cli.github.com/manual/gh_attestation_verify)、[GitHub Artifact Attestations](https://docs.github.com/en/actions/concepts/security/artifact-attestations)
- Docker摘要用于固定镜像内容；Compose文件及其间接引用具有宿主权限影响，不能无审查自动执行。[Docker镜像拉取](https://docs.docker.com/reference/cli/docker/image/pull/)、[Compose信任模型](https://docs.docker.com/compose/trust-model/)
- 单机Compose更新会重建变化的服务，不能据此承诺零停机。[Compose生产部署](https://docs.docker.com/compose/how-tos/production/)
- PostgreSQL逻辑dump在单库范围内部一致，不备份集群角色/表空间；多数据源的一致检查点仍由本项目协调。备份角色最小化并限制restore权限，未经信任的dump不在生产直接执行。[PostgreSQL SQL Dump](https://www.postgresql.org/docs/current/backup-dump.html)

这些来源支持相应机制；本篇维护策略、权限Gate、时长/资源阈值和状态机是本项目设计选择，需真实演练验证。
