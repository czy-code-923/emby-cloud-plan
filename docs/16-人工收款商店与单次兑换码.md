# 16 人工收款、商品销售与单次兑换码（v5.2）

本篇取代旧稿将所有购买统一写成Stars自动到账的假设。目标是独立网页商店默认支付宝口令红包，可同时配置支付宝、微信收款码；用户提交付款申请，管理员核实实际到账后发货，默认发一枚与商品时长对应、仅能使用一次的兑换码。它是待开发规格，不是已开通收款。

## 1. 入口与渠道

| 入口 | 购买方式 | 说明 |
|---|---|---|
| 独立浏览器网页商店 | 默认ALIPAY_RED_PACKET_MANUAL；可增ALIPAY_QR_MANUAL、WECHAT_QR_MANUAL，多渠道同时开启 | 每个订单选择一种，不代表把一单自动拆成多渠道付款 |
| Telegram购买入口 | 不提供购买按钮、跳转或独立商店网址 | 旧`/buy`、`/renew`仅说明本Bot无购买入口，不返回URL或转接现金下单 |
| TG账户、权益、码状态 | 查看本人Emby权益、预览/核销支持的单次码 | 现金价格、渠道、完整订单/退款在独立网页；付费码适用仍待确认 |
| 管理员核款 | 独立强认证后台；TG只作待办提醒 | 消息按钮不能直接一键确认到账 |

最新产品分工：现金商品展示、价格/优惠、限额预留、下单、付款申请、核款、发码与完整订单/退款全部在独立网站；运营者手动告知网址，Bot/Mini App不分发它。TG保留免费的账户、积分兑换、本人Emby权益及单次码能力，不启用Stars或另一套现金结账。Stars SKU仅停用历史候选，不能据此显示可购买按钮。

核验结论：官方FAQ与条款约束TG内数字销售，[BotNews第90条](https://t.me/BotNews/90)还提到为Bot/Mini App在外站卖的同类数字服务也应提供Stars。没有找到本项目“外链购买＋TG兑码”的明确豁免，因此按用户备选删除购买外链。外部Emby服务和免费管理Bot是否构成该规则的具体情形仍未获平台个案确认；去掉外链、人工告知网址或改成码都不自动证明合规。完整证据见[本次核验报告](../analysis/telegram-commerce-review-2026-11-13.md)、[支付FAQ](https://core.telegram.org/bots/payments-stars)和[条款6.2](https://telegram.org/tos/bot-developers#6-2-digital-goods-and-services)。

### 1.1 独立网页与TG账户服务的分工

```text
运营者手动告知独立网址（Bot/Mini App不提供购买跳转）
→ 用户自行访问网页并验证/绑定UID → 选月注册/年注册/续期/白名单商品
→ 网页生成订单和容量预留 → 选付款渠道 → 提交付款申请
→ 管理员核实本方实际到账 → 网页订单交付单次码
→ 本人取得码 → 在获准启用的核销入口预览→明确确认
→ 事务核销一次 → 创建/顺延对应grant → Emby同步 → TG/网页均可查结果
```

独立商店使用已验证HTTPS域，用户自行访问，不把地址放到Bot按钮、简介、命令、帮助、公告或自动回复。Bot所打开的账户Mini App不得显示商店导航、现金价目/二维码、共享页脚购买URL或转接到付款路由；仅前端隐藏不够，服务端的TG audience也拒绝现金结账接口。管理核款专用通知/内部后台不是面向用户的销售入口，仍需独立鉴权。

网页标准独立认证/绑定后才建单，UID与权益仍共用后端事实，不能分出第二钱包/账本。退款/付款争议在网页和人工客服处理；TG只显示本人权益、码是否已处理及必要的支持状态，不展示现金订单价格/渠道，也不附购买/订单网页链接。网页核准发码不开始时长，不替用户自动核销。

单次码能力保留，但免费/管理员赠送码和现金购买码按来源区分。付费Emby码在TG的适用未获确认，生产开关默认关闭；若需完全分离，可先在独立网页核销，Bot仅查询更新后的Emby权益。后续只有在明确适用范围后才单独启用TG付费码；关闭入口不没收已售价值，网页/人工对账和售后仍可处理。

TG输入码先做归属/状态校验并显示类型、30/365天等时长、是否包含注册、免保号效果和生效/顺延预览；确认票据绑定UID、码摘要、商品/权益版本、用途、nonce和短时截止（提案2分钟）。用户确认后再锁码/订单检查退款、容量与最新权益并原子claim；预览不耗码，确认重试返回原claim，不增加第二份时长。未注册者仅能核销含注册资格的码；安全封禁不能靠码解除。

兑换码仅在已允许来源的本人私聊/HTTPS面板处理，群聊导向私聊且不回显原码；inbound_updates、错误/审计/访问日志不得保存可重放原码，仅持久化处理所需摘要/加密短存。来源被限制时给出不泄露商店URL的支持说明；删除购买外链不撤销既有claim/grant、已售码的网页核销和退款责任。

个人静态码的远程收款、经营用途有适用限制；渠道配置需记录账号类型、提供方适用确认、允许场景、限额与复核日期。未确认时保留草稿、不发布该码；有经营收款需求时使用提供方允许的个人经营/商户产品，不把“个人码”写成无限制远程商业通道。红包也不被假定能绕过账户条款。[收款条码规定](https://fgw.sh.gov.cn/ys-hqjrfw-1.3.2.2/20240820/0d9e7b70104d4660a8d7881ed50ed914.html)

后台可多选启用、设置默认/排序、每商品限制可用渠道、单渠道暂停、收款人脱敏名、服务时间、说明和版本。默认渠道关闭时只在当前已发布可用渠道中提示用户重选，不能偷偷换收款人。全关闭则显示“现金购买暂停”，积分兑换、本人历史查单和售后保持可用。

## 2. 商品类型与确切效果

| 类型 | 默认效果 | 资格与限制 |
|---|---|---|
| 月注册码 | 新账号注册资格＋30×24小时免保号播放 | 限未开通者，预留一个注册/活跃席位；不得只交“注册资格”而漏时长 |
| 年注册码 | 新账号注册资格＋365×24小时免保号播放 | 同上，年度非自然年；无永久保证 |
| 续期码 | 已有账号追加30/90/365天免保号播放，可新增时长SKU | 默认不含注册资格；普通不活跃冻结可恢复，安全封禁不可解除 |
| 限期白名单 | 明确期限内免活动考核，默认365天，可配30/90天 | 必须同时写是否含播放、是否含注册；不额外给无限设备/同播 |
| 永久白名单 | Owner特批的无固定到期免活动授权 | 默认不售、不作永久服务承诺；上架须单独定义服务终止/退款及承载义务 |
| 积分商品 | 原300/850/3000分兑换30/90/365天免保号 | 直接生成grant；不因现金改成人工审核就改为人工扣分 |
| 资料保留/设备/同播附加包 | 仅明确写出的范围 | 不把资料保留当播放；未验证硬准入不售额外设备/同播保证 |

“白名单”必须有类型枚举；业务免活动、客户端例外、管理访问IP、支付机构收款白名单是四种不同概念。购买业务白名单不免鉴权、风控、客户端强制策略、平台容量、退款撤销或安全封禁。

后台商品字段：SKU、标题/详情、适用身份、效果/时长、价格单位、销售入口/渠道、开始/结束、限购、总销售份额、每活动/每日份额、同时有效上限、容量资源、卡码领取期限、是否绑定购买人、退款条款、状态/版本和操作者。现金价格必须由Owner填入；示例CNY金额留空，不能把原型演示价当正式价格。

## 3. 定价、限时优惠与关闭

人民币按整数“分”保存，例如1200代表12.00元；积分整数、XTR整数另列，不浮点比较、不把三种币种自动换算。

商品/价格草稿→校验→影响预览→发布版本。管理员可调原价、活动价、开始/结束、库存、限购和展示顺序。促销区间按[start,end)，北京时间展示、UTC存储；活动结束自动恢复已配置常规价，不把下架商品重新开售。

首期同一商品最多一个可生效活动，不叠优惠券/多层折扣；重叠活动发布时报错。优惠不改变时长，除非建立新商品版本明确说明。不能用未实际采用的虚构原价制造折扣。

订单创建时快照商品、渠道版本、金额、活动、退款规则、时长、可领取期限和用户确认。默认15分钟付款窗口；窗口内维持快照价，后续改价不追补。活动最后一分钟下单可保留15分钟，但该承诺必须计入活动预留。过期后要求重下单/人工处理迟到款，不静默重算已付款金额。

关闭控制分开：隐藏商品、停止新下单、停止某渠道新付款、暂停待核款自动提醒、暂停新发码、紧急停止码核销。普通下架/活动结束只挡新订单；不取消已收款的交付责任，不作废已售未用码。紧急冻结需原因、影响名单、告知和补发/退款路径。

## 4. 份额、库存与容量

每次预留在同一事务锁SKU/活动/用户/注册容量，检查后创建reservation。购物车展示库存只作参考，提交时再次检查。

三类计数分开：

- 销售份额：未支付预留＋待核款预留＋确认收款/发码的承诺；码核销不会再扣一次销售份额。取消无资金未付单可释放；退款是否补回份额由策略明确，默认不自动补回活动抢购额度。
- 服务容量：已激活成员＋已售未兑注册码预留＋其他有效注册预留。发出未兑码也占承诺，不能卖完再告知无号可开。续期不新增注册人数，但占未来承载区间。
- 同时有效白名单：已激活授权＋未核销已售授权预留；到期可释放并重新卖席位，总销售上限不会因此被重置。

“不限制商品销售总量”不等于跳过服务硬容量；无限库存需显式配置，null/0含义不得混用。首期每单数量1，每UID一张在途人工订单，待审核容量有限（起始全服2，按实际调），防占位。后台减少份额到小于已承诺数量时显示超额并挡新增，不随机撤销历史订单或码。

容量预留至少包含resource、UID/订单/码、起止或未兑保留状态、数量、释放原因。限期白名单按覆盖区间检查峰值承诺；续期预览包含未来区间和免费回退预留，不能只看付款时在线人数。首期按保守已承诺成员数管理即可，不宣称已经有预测观影负载的智能超售能力。

## 5. 人工付款与审核状态机

```text
订单：CREATED → AWAITING_PAYMENT → PAYMENT_REVIEW
      → PAID_CONFIRMED → FULFILLMENT_QUEUED → CODE_ISSUED
      → REDEEMED（另有Emby同步状态）
分支：UNPAID_EXPIRED / USER_CANCELLED_UNPAID / NEEDS_EVIDENCE
      PAYMENT_MISMATCH / MANUAL_HOLD / REFUND_PENDING / REFUNDED
```

订单、付款尝试、核款决定、发码、码核销与Emby同步独立记录。用户点“已付款”、上传截图、提交口令，只能进入待核实，不能直接变成PAID_CONFIRMED。

未注册购买者先建立可认证业务UID：采用独立网站标准登录/已验证Telegram身份绑定，服务端验证身份并生成host-only会话；不能仅提交TG数字ID、付款人姓名或截图就认领UID。已有身份跨网页/TG仍映射同一UID，网站登录不索取Telegram密码/短信码。注册码核销前无需Emby账号；丢失网页会话可以重新认证找回本人订单。

**口令红包**：用户在支付宝官方App按订单金额生成可实际领取的现金红包，独立HTTPS订单页提交口令和其页面显示的截止等必要信息；不索取支付宝支付密码、短信码、Cookie或登录授权。消费优惠券/随机拼手气金额不能自动当成等额付款。管理员在自己官方App手动领取并核对本方真实到账、金额、时间及交易引用，再确认。系统不自动登录支付宝、猜口令或调用非公开抢红包接口。

口令是可支取价值的秘密：加密短存、仅有领取权限的核款员在MFA后查看，访问有审计；不发到TG群、日志、URL、客服工单或备份通用导出。后台只显示“待查看口令”；领取或失效后尽快删除原文，默认结案24小时内清除；保留脱敏核款结果和必要凭据。默认排除口令明文/可解密密文的异地业务导出，避免把还有效的口令扩散到备机。红包有效期和可撤回/自动退回以实际App为准，本方案不臆定统一24小时规则。

**静态收款码**：订单显示固定收款人提示、应付金额、备注要求（提供方支持时）与二维码版本。用户在官方App付款，提交交易号/时间/金额和可选截图；截图只是辅助证据。管理员查本人真实收款账单，不凭截图/OCR/用户姓名直接核准。付款备注可能缺失，同金额、多人相同尾号不能自动匹配。

核款表单：本单应付/实收、渠道/收款账号、提供方唯一交易引用、到账时间、核款人、证据引用、版本与差异原因。唯一约束(provider,receiving_account,external_transaction_ref)阻止一笔到账重复给多单发货；口令摘要只能辅助查重，不是到账凭证。

首期不自动拆单/合并付款；少付、多付、第三方代付、重复转账、错收款人、红包被他人领、过期退回均入差异队列。管理员确认实收后明确补差、全额退回或另建调整单，不能编辑订单原应付金额抹平差异。

默认付款窗口15分钟；提交待核后预留保留至人工结案。显示人工响应目标（起始24小时，运营时段可调），接近用户填写的红包截止优先提醒。审核积压、负责人离线或预计不能及时领取时暂停新收款，不让口令已失效还诱导继续付款。过期未到账可关闭并释放；已提交但到账状态不明转MANUAL_HOLD，不自动当作未付抹账。窗口外实际到账仍进入迟到款队列，履约或退款，不再要求重复付。

## 6. 管理员通知和核准

渠道可多选：指定TG管理员私聊、受限运维群（仅脱敏摘要）、后台未读中心；可选邮件/HTTPS Webhook，配置后才发送。至少有后台待办，TG失败不丢订单；发件箱持久化、按订单/阶段去重、退避重试，收不到时告警。

通知只含订单号、应付金额、渠道、提交时间、待办链接，不含红包口令、完整交易截图、完整付款人身份和兑换码。默认提交即提醒，2小时未处理一次升级，24小时进入超时告警；可按营业时间调，但支付责任不因静默消失。相同失败不每分钟刷屏。

待办链接不是授权；登录＋核款RBAC＋管理员MFA后才能查看并提交。锁定接单有到期租约，避免两名管理员重复领取红包；“到账确认”使用expected_version和幂等键。大额/变更收款人/手工无单补发可要求第二人；单Owner必须明确独立复核缺失，改用再次验证与完整审计。

核款员可确认到账，不可改商品价格或读网盘凭据；发布收款码、调价、无限库存、永久白名单和退款另按权限处理。退回不应让有核款权的普通客服随便指定新收款账户。

## 7. 默认发货：单次使用兑换码

每个已核准订单项生成一条`CODE`履约，唯一(order_item_id,fulfillment_kind)。生成码、记录价格/效果快照、确认库存承诺、写交付outbox同事务；随机码至少128bit，使用安全随机源。默认max_claims=1，绑定购买UID，禁止匿名领走或群里先到先得。

码核验采用HMAC/哈希；为支持已购用户重新查看与通知重发，可另存**分离密钥加密**的交付原文，只允许本人再次认证后取，默认核销/退款后删除。这样不再宣称“只存哈希却还能重发原码”。通知默认告知“兑换码已到账，请到本人订单查看”，不把原码发群；下载/查看响应no-store、不进URL。

v5.2现金订单的用户交付提醒只在独立网站消息中心，不经用户Bot发送购买/订单/交付跳转或码原文；上段“本人订单”指独立网站。管理员脱敏核款待办的私密TG通知仍可独立启用。账户安全/Emby权益正常同步通知不等于现金订单推广，两类outbox模板与权限分开。

发货不是启用：码状态ISSUED → CLAIMED / REVOKED / REPLACED；消息DELIVERY_PENDING/NOTIFIED另列。30/365天默认从**核销成功**起算（续期按既有连续覆盖终点顺延），不从付款/发码起算。默认核销期限发码后30天，价格、效果和领取人已锁定；到期未核销转人工处理，不能自动没收已付款价值或继续无限占售卖承诺。

注册码只允许未开通身份核销；误购已有账号不自动新建第二号，提供等值转换预览或退款审核。续期码无注册资格时不创建账号。售卖后一般注册入口关闭不作废已售注册码；独立`honor_sold_registration_codes`默认true，仍需防安全封禁和保持预留容量。

兑换事务锁码、订单/退款状态、UID和容量，写claim、创建/关联membership、发独立grant和outbox后提交。两端同时兑同一码仅一次成功；本人重试返回原结果，不重复顺延。Emby失败状态为“权益已记录，同步中”，码已核销，不让用户换码/重付；worker幂等补应用。

首次发货失败补发相同交付通知，不能每次生成新可用码。确需换码时在同事务撤销旧码、创建继承同份承诺的新码；已核销不得直接再补一枚，只能走有原因的补偿grant/订单。默认不支持赠送转让；未来开启须购买人step-up、核销前变更一次指定UID并保留审计。

## 8. 退款、撤销与对账

首期按订单全额退款；少/多付差异通过独立款项调整处理。先锁码并进入退款待办，阻止“退款与核销同时成功”。未核销撤销码；已核销按公开条款计算可退性，撤销对应grant/附加权限，不直接减少总到期字段。人工渠道在官方App实际退款/转回后登记真实引用和金额，不能只点按钮就显示已退。

原渠道可核实原收款人的退款优先；红包领取后是否可原路退回由实际产品能力决定，若需手动转回，必须验证原付款关系、确认接收方并二次认证，记录回款凭证。用户聊天发一个新二维码不能自动改退款去向。退款待查不反复转出；同一退款操作有唯一号。

每天核对渠道实收/实退、已核准订单、发码、核销、grant和未决差异；人工收款无可信自动API时明确为人工账单对账，不承诺自动秒到账。已收未发码5分钟告警，待核款按人工SLA另算；通知失败独立补发。恢复旧备份前要对照独立交易/码核销撤销记录，禁止重发历史已用码。

## 9. 上线用例

- 同一付款交易引用报两单、两名核款员同时确认、重复点击发货：只留一笔有效收款分配和一份码。
- 最后一份月注册被两人抢：只成功预留一份；付款后管理员下架不取消原交付。
- 活动截止/调价/换收款码：旧未过期订单仍按快照，过期真实付款转迟到队列。
- 红包失效/优惠券/被别人领/截图伪造/少付多付：不能直接核准。
- 发码后30天未兑、已封禁购买、码并发核销、退款与核销并发：有明确结果和人工路径。
- 发码通知失败、Emby同步失败、备份恢复后重试：不双码、不双grant、不要求重付。
- 收款渠道全关、审核积压、外部通知故障：停售与查单/售后分开，后台保留待办。
- 从v5.1迁移时撤下旧购买按钮/命令文案，失效旧回调、刷新菜单/配置缓存，检查共享页脚/帮助；已复制或转发的网址不能保证撤回，不宣称能删除所有历史副本。
